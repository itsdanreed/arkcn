## How it works

A filter builder with one All/Any dropdown per group. All requires every immediate condition or child group to match; Any requires at least one. Each condition reads field, then a plain-language operator, then a value. Negation lives in the operator wording, and order never matters. Incomplete conditions are flagged with `data-incomplete` and dropped by `pruneQuery` rather than erroring.

The primitive never interprets the tree. You own the `QueryGroup` value (`{ id, match, rules }` with nested groups) and render it recursively from the parts; the root applies edits and calls `onValueChange`. Turning the tree into SQL, an API payload, or an in-memory predicate is your job, and the demo has an interpreter you can copy.

## Fields and operators

Fields are data: `{ name, label, type, options, operators, placeholder }` with types `text`, `number`, `date`, `boolean`, and `select`. `defaultOperators` covers the usual set (`is`, `is not`, `contains`, `is after`, `is between`, `is any of`, `is empty`, and so on) with an `arity` of none, one, two, or many; pass your own list to add or restrict.

## Parts

`QueryBuilder.Group group={group}` provides the logical scope and gets the same treatment at every depth: a `GroupHeader` sentence ("Match **all** of the following"; nested groups say "Where") whose only control is the small `Match` select, plus a `RemoveTrigger` for nested groups. Below it an indented `GroupBody` lists the conditions, and a `GroupFooter` holds `AddRuleTrigger` and the quieter `AddGroupTrigger` (hidden at `maxDepth`). There are no cards. Each group draws one continuous thread line from under its header past its conditions to its add row, and a nested group is indented 24px with extra space above and below, so the blocks read at a glance.

`GroupBody` is a four-column grid (field, operator, value, actions) and every `QueryBuilder.Rule rule={rule}` is a subgrid row of it, so fields and operators line up down the group, the value editor fills the remaining width instead of wrapping under the field, and `RuleActions` sits in a trailing column directly after the value, so the trash button reads as that row's own rather than floating at the far edge. A nested group spans the full row and starts its own grid; its trash button follows the header sentence. The trash icon (not an ×) keeps it distinct from the clear buttons inside pickers. It is visible at rest in muted color so touch users can find it; hover and keyboard focus bring it to full strength.

`Rule` composes `FieldSelect`, `OperatorSelect`, `ValueEditor`, and `RuleActions`. The value editor follows field type and operator arity: text and number inputs, the toolkit `DatePicker` (typed input plus calendar and clear triggers) for dates, two separate date pickers joined by "and" for "is between", a single or multiple `Select` for option fields, and a comma-separated input for free-text lists; a render-prop child can override it. Embedded inputs and selects are the standard arkcn controls, untouched: the query builder only constrains their widths. Editors show a placeholder ("Enter a value", "Choose a value…") while a condition is incomplete.

`QueryBuilder.Summary` is a footer under the rows (hairline above, muted sentence) with the conditions in foreground color and each value emphasised and kept on one line: text and option values are quoted, dates read as "Oct 1, 2026", list operators read "Plan is “Free” or “Pro”", three or more conditions are comma-separated ("A, B, and C"), and Any groups read "either A, or B". The same sentence is available as `describeQuery` (a string) or `describeQuerySegments` (text and value segments for your own markup). Unfinished conditions are counted separately ("1 incomplete condition not applied") so a half-built filter is never mistaken for a complete one; `pruneQuery` omits them and `countIncomplete` returns the number.
